# 决策合议庭 · AI Council

> 发布名：**决策合议庭**（备选：**多模型决策庭**）。技术 slug 仍为 `ai-council`，不要改。

一个问题，多家厂商，同时作答，看它们在哪里一致、在哪里分裂。

**核心判断**：一致的部分通常是常识，不值钱；分裂的部分才是洞察。

## 运行依赖（首次使用前必读）

### 为什么用硅基流动，而不用 WorkBuddy 自带的十几个模型？
这是被问得最多的问题，先说清楚——**不是不能用，是硅基流动对「无会员、要省积分」的你更合适**：

1. **架构不同（根因）**：本 skill 的 `council.py` 是一个**独立 Python 进程**，靠 HTTP 直接调
   OpenAI 兼容接口拉起 9 家模型并发。它要的是一个"别人家的、带 key 的 HTTP 端点"。
   WorkBuddy 内置模型是**平台运行时的一部分**，没有对外暴露的裸 HTTP 端点给外部脚本调——
   它们只在「你跟我（助理）对话」时由平台在背后用，独立脚本调不到。
2. **计费不同（你的硬约束）**：内置模型走**平台积分**；你明确说过"没有会员、要省积分"。
   硅基流动用自己的 key（有免费额度），**跑 9 家并发几乎零平台成本**，正好贴合你的要求。
3. **功能不同（本 skill 的灵魂）**：陪审团要的是「9 家不同厂商、互不串通的独立判断」。
   硅基流动一个 key 覆盖 DeepSeek / Qwen / Kimi / 阶跃 / 智谱 / MiniMax 等一整批开源模型；
   而内置模型是平台挑的一组，且助理在任一时刻只能「是」某一个模型，无法同时扮演 9 个独立裁判。

> 例外：若你不在乎积分、且愿意把本 skill 重写成「宿主模式」（由 WorkBuddy 助理当主持人、
> 逐个调内置模型），可以不用硅基流动——但那会烧积分、且失去跨厂商多样性，默认不推荐。

### 条件式接入流程（已接入则跳过，未接入才要求）
**第 0 步 · 先自检**：看 `models.json`（`~/.workbuddy/models.json`）里是否已有 `url` 含
`siliconflow` 的条目。
- **有** → 你已完成接入，本 skill 直接可用，**不用装任何东西、free-llm-setup 也用不上**。
- **没有** → 走下面二选一。

**第 1 步 · 没有 key 时（二选一）**
- ① **一键接入（推荐）**：让 AI 加载作者配套 skill **`free-llm-setup`（免费大模型一键接入）**，
  选「硅基流动」路线，它会把你申请的 key + 实测通过的模型自动写进**同一个** models.json。
  **安全合并**：它只追加/刷新自己管理的硅基流动条目，不会删除你已有的其他 provider
  （如 OpenRouter / Gemini）配置；同 id 条目会被更新而非重复写入。所以即使已接入、手滑又跑一次，也不会破坏你原有设置。
  ```bash
  python ~/.workbuddy/skills/free-llm-setup/scripts/setup_free_llm.py --provider 1 --key sk-xxxx
  ```
- ② **手动申请**：去 siliconflow.cn → 控制台「API 密钥」→ 新建（有免费额度），然后让 AI 代跑上面命令，
  或手动往 models.json 的 `models` 数组加一条（`url` 含 `siliconflow`、有合法 `apiKey` 即可）：
  ```json
  {"id":"deepseek-ai/DeepSeek-V3","name":"DeepSeek V3 (硅基流动)",
   "vendor":"DeepSeek","apiKey":"sk-xxxx",
   "url":"https://api.siliconflow.cn/v1/chat/completions","supportsToolCall":true}
  ```
跑完**完整退出并重开 WorkBuddy** 让配置生效。

### 注意
- 脚本只读 `models.json`（同时兼容 `~/.codebuddy/models.json`），从含 `siliconflow` 的条目取 `apiKey`；
  读不到就报 `models.json 里找不到硅基流动的 key`。
- 脚本只负责调模型，**不联网抓外部信息**（见「零之三」共享调研员机制，那是主持人做的事）。
- 模型池（`POOL`）里的 10 家随时可能失效，跑前用 `scripts/probe.py` 探活，
  别无脑信 models.json 里已有的条目（实测某轮 6 个里只活 1 个）。

## 零、六条沙箱规则（最高优先级，违反即作废）

陪审团不能问诱导性问题。**AI 更不能揣摩用户的内心倾向**。
优质答案的本质是打破倾向，不是迎合倾向。分发前逐条检查提示词：

| # | 禁止 | 允许 |
|---|---|---|
| 1 | 用户的猜测、情绪、判断（"我觉得她在骗我"） | 已发生的行为（"她在第八天打了这个电话"） |
| 2 | 身份标签与光环（"知名女演员""身家 85 亿的富豪"） | 可核验数字（"她 34 岁""他可支配资金 85 亿"） |
| 3 | 列选项让人挑（"A、B、C 我该选哪个"） | 单一开放问题（"该不该给"） |
| 4 | 任何期望答案的暗示 | — |
| 5 | 让模型评价提问者本人 | — |
| 6 | 提示词里出现"我倾向于""我想要的是" | 删掉，或改写成客观约束 |

**对模型的额外禁令**（写进 system prompt，缺一不可）：
- 不得推测提问者的心理、动机、期望
- 不得出现"您可能希望""如果您在意的是""建议您考虑"
- 不得先复述用户立场再回答（复述即锚定）
- 不得在给出结论前征求认同
- 不得因为问题涉及情感就软化判断

**AI 助手这边的义务**：用户给的原始叙述几乎必然带倾向。
**分发前必须做一次"事实化改写"** —— 剥掉形容词、情绪和评价，
只留时间、地点、金额、数量、已发生的行为、客观约束。这一步不能省。

## 零之二、事实复核轮（提问之前，必须过这一关）

**用户口述必然有笔误、有含糊、有前后矛盾。拿没核实过的事实去提问，
问出来的就是废问题——偏差会在第一步就传下去，后面全白搭。**

事实化改写之后、抽签提问之前，必须把改写结果**回显给用户确认**，并明确列出：

1. **我记录了什么**——逐条编号，时间/金额/数量/行为分开列
2. **我删掉了什么**——哪些形容词、情绪、判断被剥掉了（让用户知道没被曲解）
3. **我发现的矛盾**——数字对不上、时间对不上、前后不一致的地方，直接点出来
4. **不确定项**——原话里"应该""可能""忘了"这类，单独标成待确认

必须明确问一句：**"以上对吗？哪里要改？"** 用户点头了才进提问环节。

实测教训（2026-08-30 电动车案）：用户说"用了 20 天"但"8 月 5 日购入"，
按当天算是 25 天——这种矛盾不复核就会原样喂给模型。
另有一次漏掉了用户随口提的关键事实（"忘了有没有说过底价"），
补上之后才问出了决定性的一问。**随口一提的往往最要紧。**

## 零之三、外部信息委托（共享调研员）

**问题来源（呼吸机回收案暴露）**：陪审团模型走的是纯对话接口（硅基流动等），
**没有浏览器、没有实时数据**，物理上查不了"现在这台二手呼吸机值多少"。
结果所有家都拿"7500 元购入价"当基数做折旧，没有一家去比对当前行情——
锚定偏差 + 无工具，双重失误。

**本质**：价格随行就市、政策随时变、案情有最新进展——这类事实
**不存在于模型的训练数据里**，必须由外部检索喂入。不能指望模型"自己去查"，
因为它没有那个工具。

### 方案：共享调研员（delegate-to-browser）

本 skill 运行在 WorkBuddy 里，而 WorkBuddy **自带浏览器能力**
（WebSearch / WebFetch / agent-browser）。把"查外部信息"这件事从陪审团模型手里
拿过来，交给 WorkBuddy 这个**共享调研员**统一做：

1. **陪审团模型只发需求，不自己查。** 在澄清轮或投票轮，模型若需要外部事实，
   输出一个结构化请求：
   ```
   [[NEED: 当前二手瑞思迈 AirCurve 10 VAuto 双水平呼吸机成交价区间]]
   ```
2. **主持人（WorkBuddy / 法官模型）统一收单。** 收集所有 `[[NEED]]`，去重，
   批量用自身的联网工具检索。
3. **返回原始材料，不返回结论。** 调研员只给**检索原文片段 + 来源 URL**，
   绝不给"所以我判断价格是 X"这种消化过的结论。**这是铁律**——
   否则调研员就变成了一个隐藏的第十个裁判，把它的取舍悄悄塞进事实里。
4. **共享注入。** 把原始材料汇总成 `external_context` 块，在下一轮投票时
   **对全体陪审团成员同时可见**。一次查询、全员共用，省调用、也保证各家看到的是
   同一份事实（避免 A 看到价 X、B 看到价 Y 的不一致）。
5. **有界。** 最多 1 轮检索、最多 N 条（默认 6）查询；检索结果作为补充事实，
   不替代用户已确认的事实。

### 为什么比"静态预注入行情"更好

早一版方案是"投票前由主持人先抓一波当前行情写进 facts"。那版有两个死穴：
- **猜不准要查什么**：价格只是其中一种外部事实。用户说"还有很多其他要求都要看
  最新资讯"——政策、法规、竞品、当事人最新动态，预先抓不全。
- **假设驱动**：主持人替模型决定了"你需要什么"，模型真正卡住的点反而可能没覆盖。

共享调研员是**需求驱动**：模型在自己推理时发现自己缺哪块外部事实，就发哪一单。
它**包含了**静态预注入（价格类需求天然会被提出），但是更通用、更完整。

### 护栏（不写会翻车）

- **原始不消化**：调研员返回原文片段 + URL，不下结论。法官/主持人不得对检索结果
  做"这意味着…"的摘要后喂给模型。
- **有界防循环**：限定 1 轮、N 条，禁止模型用 `[[NEED]]` 无限追查导致上下文爆炸
  和积分烧穿。
- **裁判隔离不变**：调研员是基础设施，不是投票人。它只搬事实，不评分、不站队。
  与第五节"计票人不能是选手"同一原则。
- **模型仍对推理负责**：浏览器只补事实，不替模型思考。发现模型把"去查"当"甩锅"
  （自己不推理只发 NEED）要回退到规则打分里"可执行/推理链"维度扣分。
- **失败降级**：检索无结果/被墙，明确告知模型"无外部数据可用"，模型须基于已确认
  事实作答并标注不确定性，不得编造。

### 实现说明（重要）

`scripts/council.py` 是独立脚本，只调 API 池，**调不了 WorkBuddy 的浏览器工具**。
所以本机制的实际跑法是：

- **主持人驱动模式（推荐）**：由 WorkBuddy 这个会话本身当主持人。跑 `clarify` 拿到
  模型提问后，若某问/某答暴露出需要外部事实，主持人直接用自身 WebSearch/WebFetch
  抓取，把原文片段写进 `facts.txt` 的 `[外部事实]` 段，再跑 `vote`。`[[NEED]]` 是人与
  主持人之间的约定格式，方便主持人识别"模型缺什么"。
- **纯脚本模式**：脚本负责跑模型并发出 `[[NEED]]` 标记；主持人（人或 AI）看到标记后
  补足 `external_context` 再继续。脚本本身不联网。

### 机制验证案例（呼吸机回收案，2026-08-30，有真实对比）

**为什么需要这个案例**：上面这套机制是回应一个具体失败长出来的——
最初跑呼吸机回收价时，「外部信息委托」还没加，结果错得很有代表性。把它记在这里，
以后（包括作者自己）翻文档能一眼看懂"这个机制当初是为了兜住什么"。

**失败现场（旧 run，无共享调研员）**：

- 案情：朋友父亲 2023.1 疫情峰值期花 **7500 元**购入瑞思迈双水平呼吸机，父故后朋友愿由当事人回收转赠家人。
- 流程跑完后，9 家陪审团**全部拿 7500 当基数做折旧**（40%–60% → 3000–4500），**没有任何一家去比对当前二手行情**。
- 加权均价 ¥1,697。结论方向碰巧不离谱，但**方法是错的**——锚定历史买价，等于用疫情峰值虚高原价折旧。
- 用户的原话点破了要害："如果是一台汽车买在高点、后来市场跌了，你按原价折旧卖，我亏死。"

**修正现场（新 run，启用共享调研员）**：

1. 用户补充关键事实：型号应为 **S9 VPAP ST**（旧 run 误写 S2，查无此机，是最大的错锚源）。
2. 主持人（WorkBuddy 会话）当共享调研员，联网抓回**原始行情**写进 facts 的 `[外部事实]`：
   - 新机零售：官网 S9 VPAP S/ST 指导价 ¥6,980 / 天猫 ¥5,833（历史最低 ¥5,783）
   - 国际二手未使用：DOTmed $595≈¥4,280、Medbidding $830≈¥5,960、认证翻新 $1,099≈¥7,900
   - 行业：二手呼吸机交易指数 2024 Q4 同比 −19.7%，拍卖流标率 43%
3. 同一批 9 家、同一套质询与回答，仅 Q4（型号识别）结论更新为"已可对应在售真机型"。
4. 投票墙钟 128s（无 429，与旧 run 持平）。

**对比结果**：

| 指标 | 旧 run（无调研员） | 新 run（有调研员） | 变化 |
|---|---|---|---|
| 9 家是否锚定 7500 历史买价 | **9/9 锚定** | **0/9 锚定** | 全部切到当前市场价 |
| 加权均价 | ¥1,697 | **¥2,762** | +63% |
| 中位数 | ¥2,000 | ¥2,750 | +38% |
| 简单均值 | ¥1,861 | ¥2,913 | +57% |
| 核心簇均值（去两极端 6 家） | ¥1,857 | ¥2,831 | +53% |

**这个案例证明了什么**：

- 锚定偏差**真实存在且必然发生**——没有外部数据时，模型 100% 被你给的历史买价带跑。
- **机制能兜住它**——只要主持人把真实行情作为原始数据注入，9 家立刻集体改锚，不需要任何单模型变聪明。
- **代价极小**——只多一次主持人检索（约 1 分钟）、9 家共用，投票耗时不变。
- **上调不是行情涨了，是错锚被修掉**：旧 run 的折价有两层（锚定 7500 + 型号未知当高风险）；新 run 两层都消除，所以数字涨了。这提醒读者——看机制效果要区分"锚点修正"和"真实行情变化"，别把错锚消除当成市场上涨。

> 一句话留给后人：**凡涉及价格波动资产，先让共享调研员注入当前行情，再投票。否则模型会拿你给的历史价当真理。**

## 一、模型池（从本机 models.json 动态加载，不写死）

**陪审团模型直接读 `~/.workbuddy/models.json` 里所有带 `apiKey` 且 `url` 为 OpenAI 兼容端点的条目**（硅基流动、OpenRouter、Gemini 等均可）——不再写死模型名。早期版本把 `DeepSeek-V4-Flash / Kimi-K2.7-Code / Qwen3.5-397B` 这类虚构版本号写进代码，在硅基流动真实 API 上全部 404，换电脑就跑不通；改成读你自己的配置后，模型名一定真实可用。

厂商（vendor）由模型 id 前缀推断（`Qwen/`→阿里通义、`deepseek-ai/`→DeepSeek、`THUDM/`→智谱…），用于抽签分层保证多样性；想让陪审团更大更跨厂商，就在 models.json 多配几家硅基流动模型（运行 `free-llm-setup` 选「硅基流动」路线可一键配齐），配置即生效、无需改代码。跑前可用 `scripts/probe.py` 探活，死模型会标 `[FAIL]`。

（无需在代码里列模型清单——脚本自动读取你 models.json 里的硅基流动条目组成陪审团，多配一家就多一位陪审员。）

**有 VPN / 有海外 key 的用户，把 OpenRouter、OpenAI、Anthropic、Google 一并加进池子。**
国产模型之间同质化严重（同一套价值观、同一套安全对齐），
国际模型掺进来才能真正打破共识。`kind` 字段用于抽签配额。

### 跑之前必须先问用户用哪一档

成本敏感的用户（没会员、省积分）需要被提前告知。开工前问一句：

| 档 | 用什么 | 成本 |
|---|---|---|
| 一档 | 你配置的硅基流动模型（数量 = 你 models.json 里配了几家） | 几分钱 |
| 二档 | 加国内付费模型（消耗 WorkBuddy 积分） | 需用户同意 |
| 三档 | 加国外模型（GPT / Claude / Gemini / Grok） | 需 key + 可能走代理 |

**不要默认烧用户的积分。**

### 突破 API 池：`pack` 子命令

脚本只能调 API 池里的模型，但**用户在 WorkBuddy 里可以手切模型**——
这是白捡的额外席位。做法：

```bash
python council.py pack --facts facts.txt --question "…" --out case1
```

生成 `pack.md`，里面是系统提示 + 事实 + 问题的完整文本。
用户把它粘进 WorkBuddy 内置模型（换一个模型跑一次）、ChatGPT、Claude 或任何 AI，
**把回答整段复制回来**，由 AI 并入计票。

这样理论上能把陪审团扩到任意多家，且不受 API key 和网络的限制。
注意：拿回来的答案同样要过一遍证据权重，立场一致才合并。

> 注意：硅基流动上的模型可用性随时在变（下架、配额、区域限制），**不要在任何地方写死"哪些可用 / 哪些失效"的清单**。
> 本技能直接读你 `models.json` 里配置的硅基流动条目当陪审团；跑前用 `scripts/probe.py` 探活，
> 死模型会标 `[FAIL]`，发现大面积失败就去 models.json 换一批在线模型即可。

## 二、分层抽签（默认，不要指定成员）

固定班底会积累系统性偏见——每次都是同一批模型，等于把某几家厂商的世界观当成标准答案。

**规则**：
1. 池子按 **vendor 分层**，每家厂商最多出 1 席（防止 DeepSeek 一家占俩座）
2. 抽签决定具体是谁，本次抽签结果写进报告，**可复现**
3. 强制配额：至少 1 席 `kind=reasoning`（推理型，慢但深）
4. 席位数默认 8；池子不足 8 时全上
5. 抽签种子记录到报告里，方便复跑对照

**例外——指定模式**：用户明确要"对比这几家"时，改用指定模式，并在报告里
标注"本次为指定成员，存在常驻偏见风险"。

## 三、陪审团制：先质询，后投票（本节最要紧）

照法庭陪审团来：**先让每个成员提问，全部问完、用户答完，再集中投票。**
不是各问各的然后按顺序投，更不是问完就自动往下跑。

### 三条铁律

1. **一个成员，一个问题**——不是三个
2. **轮流提问，后问的看得到前面问过什么，且禁止重复**
   → 这是**串行**的，不是并发。信息依赖是本质，改不成并发。
   可见 + 禁重复 = **强制多样性**：浅问题被前面问掉，后面的被迫往深水区走
3. **问完必须停下来等用户**——脚本在此退出，生成 `questions.md` 等人填。
   绝不自动进入投票。**让模型带着信息缺口投票，等于白跑**
4. **投票时材料完全一致、同时发出**——所有家拿到的是同一份
   （原始事实 + 用户补充的问答），并发投票，不分先后。
   提问可以串行，投票必须同时，谁也看不到谁的答案

### 为什么提问要"可见 + 禁重复"，而不是"互不可见"

早期版本做成了互不可见 + 并发，实测很糟：7 问里「具体条件」「具体用途」
「支付方式」反复撞车，只能靠事后聚类硬合并——治标不治本，还丢信息。

改成可见 + 禁重复后，4 问零重复，且一问比一问深：

| 位次 | 问了什么 |
|---|---|
| 1 | 她要五千万时，是否说明了用途或附加条件？ |
| 2 | 转 3000 万后，是否向收款人本人核实过账户归属？ |
| 3 | 42 页材料的记载，与公开信息是否一致？ |
| 4 | **你转 3000 万，是在收到 42 页材料之前还是之后？** |

第 4 问只有第四位才问得出来——浅的都被前面问掉了。
而这一问直接决定"你是否明知有问题还给了钱"，是全场最狠的一刀。

### 阶段一 `clarify`

> 你是陪审团第 N 位成员。现在轮到你提问。
> 【前面成员已经问过的问题】……
> 硬性规则：不许重复上面任何一个问题，也不许换个说法问同一件事。
> 重复的问题会被作废。必须问一个前面没人问过的、新的角度。
> 只提事实性问题——时间、金额、数量、约束条件、已经发生的行为。

- **串行执行**，每次把已问过的问题列表塞进 prompt
- 拿到问题后做二元组相似度检测（阈值 0.34），撞车即作废并当场打印
- 排除纯推理模型（吐思考碎片）和 reasoning 类（实测 R1 单独 187 秒拖慢全场）
- `max_tokens` 给 **8192**，且失败自动重试一次（LongCat 曾思考吃光 token）
- 串行代价：7 家约 5-8 分钟。这是正确性的必要代价，不要为了快改回并发

生成 `questions.md` 后**退出**，并明确打印「停在这里等你」。

### 阶段二 `vote`

读出用户在 `questions.md` 里填的答案，以「问 / 答」形式并入 facts，
然后所有家同时投票。用户一条没填会打印警告——信息缺口未补，结论可信度下降。

### 答案怎么回来（最容易漏的一环）

**脚本停下来了，但用户填完答案后怎么交回来？这个通道必须显式设计。**
不要假设用户会去终端敲命令——大多数人填完文档，最自然的动作是回头告诉 AI 一句。

**默认走对话，不要让用户去开编辑器。** 三条通道，按推荐顺序：

1. **对话口述（默认）**——AI 把问题编号列出来，用户在对话里按编号答，
   可以是口语、可以乱序、可以只答几题。AI 负责回填 `questions.md`
2. **用户自己编辑 `questions.md`** → 说一声，AI 读文件跑 `vote`
3. **用户跑 `python council.py vote --out <目录>`** → 给习惯终端的人

**关键：回填之后必须回显确认，不能直接跑。** 用户口述必然有笔误和走形，
AI 回填时要复述一遍"我记的是这样：Q1=…、Q2=…、Q3 你说的是…我理解成…对吗？"，
**尤其要把用户的口语转写成事实陈述的部分单独标出来让用户确认**。
确认后才投票——这跟提问前的事实复核是同一条原则：**两个确认点，一个都不能省**。

**踩过的坑**：流程做完"停下来等"就以为完事了，结果用户填完不知道往哪交，
整条链断在最后一米。**凡是让人参与的环节，都要同时设计"去"和"回"两条路。**

解析答案时注意：用户经常把答案直接写在 `你的回答：` **同一行**（而不是换行），
解析必须同时支持同行和换行两种写法，否则静默读空、白跑一轮。

### 实测（2026-08-30，5000 万案例）

智谱和美团独立地问出了同一件事——「转入田心爱账户的 3000 万是否还有余额」
「有无书面或录音证据」。这两问正是后来诉讼里最要命的东西，原始材料里根本没人提。
**澄清轮的价值不只是补信息，是逼出用户自己都没意识到的盲区。**

各家问到的关键一问还包括：
「是否已核实 3000 万收款人是她亲生父母」
「她是否像上次要彩礼那样指定了具体账户和到账回复」
——都是在逼用户把口头事实变成可核验事实。

## 四、主轮 Round 1（一次只问一个）

**一个提示词里只能有一个问号。** 多问号会让模型挑软柿子答，也会互相锚定。

结构化要求只能约束"怎么答"，不能变成"再问几个问题"：

```
按这个格式答：①最坏情况 ②概率区间 ③真正的问题 ④第三条路 ⑤一句话结论
```

**情境锁定**（问已知结局的公开事件时必须用）：

> 现在是 {事发前的时间点}。你只知道我告诉你的这些事实。
> 不要用你记忆里任何关于此事的公开信息去补全——那些事要么还没发生，要么是假的。

当事人真正的纠结（往往不是主问题），**单独开一轮问**，不要塞进主问题。

## 五、证据权重制（不用一人一票）

一人一票的问题：骑墙的"都有可能"和给出可验证推理链的答案拿同样的票，
这是对用户不负责。但按"这是 GPT-5 所以权重高"加权，是把 AI 的偏见写进制度，更糟。

**权重只看这份答案本身说了什么，不看它是谁说的。**

基础分 1.0，逐项累加：

| 维度 | 判据 | 系数 |
|---|---|---|
| 判断明确 | 给出明确结论 | 骑墙即 **×0.4**（这是乘法，直接打折）|
| 可证伪 | 给出具体后果、数字、时间点 | +0.3 |
| 推理链 | 从事实推到结论，不是直接抛结论 | +0.3 |
| 可执行 | 给出下一步动作 / 条件 / 止损线 | +0.3 |
| 独立信息 | 提到别人都没看到的事实或角度 | +0.2 |

权重区间 **0.3 ~ 2.1**，再乘本次相对排名系数（前 1/3 ×1.3，后 1/3 ×0.8）。
**每一票的权重和理由必须在报告里公示**，不许黑箱。

**不按字数扣分。** 字数跟答案质量没有逻辑关系——简洁而准确的答案不该被罚，
啰嗦而空洞的不该被奖（早期版本有这条，已删）。真正的敷衍是**骑墙**和**没有具体数字**，
这两条已经单独判了。

**必须有相对排名系数。** 只看绝对分的话各家挤在 1.3~1.8，实测原始票 67% vs 加权票 66%
——加权形同虚设。切分必须用**严格名次**，不能用阈值：并列分会让「前 1/3」膨胀成「前 7/9」。

### 加权起什么作用（跟直觉相反）

加权**不是**让多数派更强，是让**质量高的那一方**更强。实测（电动车案）：

| 阵营 | 原始票 | 加权票 | 变化 |
|---|---|---|---|
| 500-510（6 家） | 67% | 66% | −1pp |
| **600+（2 家）** | **22%** | **26%** | **+4pp** |
| 不卖（1 家） | 11% | 8% | −3pp |

600+ 只有 2 家，但其中混元拿了全场最高分，所以它的占比**不降反升**。
「不卖」那家答案质量最低，被压下去。

**结论不变（仍是 500-510），但少数派的分量变重了——这才是加权该干的事。**
若某一轮加权后胜负翻转，说明少数派质量碾压多数派，那更该听少数派的。

**计票人不能是选手。** 陪审团成员不得参与给自己加分，这是底线。
默认走规则打分（纯代码，没有任何模型参与评判），天然无利益冲突。

`--judge` 启用模型裁判时，裁判**必须在陪审团池之外**，代码里用 `JUDGE_FORBIDDEN`
硬卡（任何在 `POOL` 里的模型都禁止当裁判）：裁判若在本次名单内，直接拒绝并退回规则打分。
（初版把裁判设成了 MiniMax M2.5，而它就在池子里会被抽中当陪审员——既当运动员
又当裁判员，已修。默认走规则打分，模型裁判仅 `--judge` 显式开启且需用池外模型。）

**用规则打分更好，不只是因为公正，还因为模型有审美偏见**：
模型当裁判会偏好跟自己风格像的答案（都爱长答案、都爱列点）。规则打分没这毛病。
实测对照——同一批答案，两种打分**排名一致，但尺度不同**：

| | 智谱 | 美团 | 混元 | 通义 | R1 |
|---|---|---|---|---|---|
| 规则 | 1.50 | 1.60 | 1.50 | **0.91** | 1.60 |
| 模型 | 2.10 | 1.70 | 1.70 | **1.50** | 1.70 |

差别全在通义那份 238 字的敷衍答案上——规则给了 ×0.7 惩罚，模型裁判手软。
**规则打分更狠更一致，模型裁判更宽容。**

**三种模型都不配当裁判**（2026-08-30 实测）：
- Step-3.5-Flash 是纯推理模型，`content` 恒为空，吐不出 JSON
- MiniMax 只打了 3 份里的 1 份，漏项
- Qwen3.5 直接无视"区间 0.4~2.1"，自创百分制给了 8.5 / 9.5 / 9.0

规则打分（`scripts/council.py` 的 `rule_weigh`）确定性、可复现、零额外调用，
而且每一分都能解释。两个关键阈值：
- **独立信息取 70 分位作门槛**，否则人人有份，失去区分度
- **答案 < 350 字直接 ×0.7**，惩罚敷衍作答

实测一例：推理型 R1 只答了 234 字，被压到 ×0.91；GLM-5.2 答了 1235 字四项全中，
拿满 ×2.10。**同一个模型，下次答得好权重就上得去——这才是加权该有的样子。**

**结论表述三条铁律**：
1. 同时给出**原始票数**和**加权票数**，两个都摆出来
2. 两者指向同一方 → 高置信
3. **两者指向不同方** → 必须显式警告：
   「多数派是常识，少数派才是信号」，并把少数派单独成页

第 3 条是这个技能最值钱的产出，遇到就一定要标红。

## 六、汇总顺序

1. **原始票 / 加权票** — 两个数都给
2. **分歧点** — 在哪一问上分裂了，这才是真问题
3. **少数派** — 单独一页，附权重和理由
4. **共识** — 全票通过的部分，说明答案已经写在提示词里了
5. **盲点** — 谁盯到了别人漏掉的细节
6. **对账** — 事件若有真实结局，逐条核对谁说中、谁没说中

## 七、交付

优先做**自包含 HTML 报告**（能分享、能转发、零依赖，传播成本最低）。
要 PPT 时按下方排版规范用 python-pptx 自绘（脚本未内置 PPT 模板，需自行生成）。

**不做小程序**。理由：这个工具的核心成本是 API 调用，做成小程序就得有人付 API 费——
让用户填 key 体验崩坏且有合规风险，自己垫资则日活一百就是每天几十上百元纯烧钱；
外加备案 3-4 周 + 软著，1.5-2 个月才能上线。目标用户本来就在用 AI 客户端，
小程序解决不了任何真实痛点。要扩大影响，把 HTML 报告做得能转发就够了。

**PPT 排版**：本机无 LibreOffice / PowerPoint / WPS，**无法渲染成图校验**。
生成完必须跑 `scripts/check_layout.py`（按 CJK 字宽估算文本高度 vs 框高）。
不跑必然翻车——第一次做出 9 处溢出 + 纵向越界。

- 16:9（13.333 × 7.5 in），深色底 `#0A0D14` + 单一强调色 `#E5B25D`
- 内容区上界 1.9、下界 6.8，页码固定 6.95
- 中文字体要同时设 `a:ea` 和 `a:cs`，只设 `font.name` 不生效
- 列表项高度 `(下界 - 上界 - 间距×(n-1)) / n` 自适应

## 八、调用坑位（前四条都真踩过）

1. **纯推理模型的 `content` 恒为空**：Step-3.5-Flash 就是这种。思考过程全在
   `reasoning_content` 里，拿它当答案会拿到一坨思考碎片。
   - 主轮：可以回读 `reasoning_content` 兜底（内容仍是有效思考）
   - **澄清轮和裁判轮必须禁用兜底**（`allow_reasoning=False`），并直接在选人时
     用 `pure_reasoning: True` 标记排除掉。实测它会吐出
     「这可能是临时起意还是事先…」这种半截思考，根本不是问题
2. **抽签的推理配额替换会造成一厂商两席**：补 reasoning 席位时必须替换**同厂商**
   的那一个，否则会把另一家厂商挤掉（实测把阿里通义挤没了，DeepSeek 占了俩座）
3. `max_tokens` ≥ 4096。给小了，推理模型 token 全被 thinking 吃掉，返回空串
4. DeepSeek-R1 单次约 110s，10 线程并发总耗时约 3 分钟，被它拖住；
   澄清轮只派 `kind=fast` 且非纯推理的前 5 家
5. LongCat-2.0 的 `content` 也可能为空，主轮回读 `reasoning_content` 即可，

**每跑完一次都要回头看输出**：本次全量跑就抓出了上面第 1、2 两个 bug。

## 九、实测记录（2026-08-30）

首个案例：孙宇晨《我的女友景甜》5000 万美元事件，十家全量跑通，产出 16 页 PPT。

- 情境锁定生效，十家**无一家**用后续信息作弊
- 结论 9:1，但在"给了她会不会留下来"上分裂成 6:3:1 —— 分歧点才是真问题
- 唯一说"给"的腾讯混元，方案在商业上最可执行（2000 万 + 节点结算 + 70/30 分担）
- 十家 100% 认定"这不是钱的问题"，全部抓住同一句话 —— 说明答案已写在提示词里
- 智谱、美团单独盯住了"景国庆、田心爱"两个名字；结局里这两人确为共同被告

## 十、文件

- `scripts/council.py` — 主流程：抽签 → 澄清轮 → 主轮 → 规则加权 → JSON
- `scripts/probe.py` — 探测哪些模型还活着，结果决定入池
- `scripts/check_layout.py` — 排版体检，无渲染器时的唯一防线
- `scripts/ask_all.py` — 旧版单轮脚本：读 `prompt.txt`，十家同问同提示词（备用，不进陪审团流程）

两阶段用法（中间必须人来填答案）：
```bash
# 1) 陪审团各提一问，然后停下来
python council.py clarify --facts facts.txt --question "该不该给" --seats 8 --seed 42 --out case1

# 2) 人打开 case1/questions.md 填写「你的回答」，保存

# 3) 并入答案，所有家同时投票
python council.py vote --out case1
```
主问题含多个问号时会中断并警告——这是沙箱第 3 条的硬约束。
